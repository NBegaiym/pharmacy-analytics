# Профилирование данных (Этап 1)

Источник цифр: [`etl/01_profiling.py`](../etl/01_profiling.py) — запустить `.venv/Scripts/python.exe etl/01_profiling.py`,
полный вывод в консоль занимает ~2 минуты (самый тяжёлый файл — 13, читается чанками по 1M строк).

Все CSV: разделитель `;`, кодировка `utf-8-sig`, дробная часть чисел — через запятую (`"7250,0"`), без разделителя тысяч.
Все XLSX читаются pandas/openpyxl без проблем с кодировкой.

## 2. Схема связей (ключи)

```
                      WARE_ID                          APTEKA_ID / Код / G$PROFILE_ID
        ┌───────────────────────────────┐     ┌──────────────────────────────────────────┐
        │                                │     │                                          │
03 справочник товаров ──WARE_ID──┐       │     │   ┌── 05 справочник аптек (Код)
                                  │       │     │   ├── 06 справочник аптек-коды (Код Профиля) [подмножество 05]
04 справочник товаров-кратк. ──ШК┼(~99%   │     │   └── 07 справочник аптек-города (SlCode)   [подмножество 05]
   (нет WARE_ID, джойн по        │ overlap│     │
    штрихкоду, с дублями)        │с BARCODE     │
                                  │ из 03) │     │
                          ┌───────┴────────┴─────┴──────┐
01 продажи ───────────────┤  WARE_ID, APTEKA_ID, DOCNUM  │
02 приход ─────────────────┤ WARE_ID, APTEKA_ID, DOCNUM  │
                          └──────────────────────────────┘

08-12 kaspi — БЕЗ рабочего ключа к остальным таблицам (см. п.2.1 ниже). Используется только как
              самостоятельный сетевой агрегат.

13 остатки: WARE_ID, G$PROFILE_ID (= Код аптеки), PART_ID (партия) — отдельный от 01/02 файл,
            связывается с 03/05 по WARE_ID / G$PROFILE_ID, но имеет собственную гранулярность (партия/день).
```

Ключевые находки:

- **`WARE_ID`** — сквозной ключ товара для 01, 02, 03, 13. Из 9 105 товаров, встретившихся в продажах/приходе,
  только **3** отсутствуют в справочнике 03 → справочник товаров практически полный (99.97% покрытие).
- **`APTEKA_ID`** (в 01/02) = **`Код`** (в 05/06) = **`G$PROFILE_ID`** (в 13) — один и тот же код аптеки во всех файлах,
  просто называется по-разному. Все аптеки, встречающиеся в продажах/приходе, есть в справочнике 05 (0 несовпадений).
- **`DOCNUM`** — номер документа. Внутри 01 уникален в рамках аптеки (ни один DOCNUM не встречается в двух разных
  аптеках), поэтому его можно использовать как ключ чека для basket-анализа.

### 2.1. Kaspi (08-12) — отдельная таблица без рабочего ключа к остальным файлам

Первая проверка выглядела многообещающе: колонка "№ документа Покупки/Возврата" в Kaspi-файлах на **100%**
совпадает со значениями `DOCNUM` из продаж. На основании этого казалось логичным строить `payment_mix` в разрезе
аптеки/сотрудника через этот джойн. **Это оказалось ложным срабатыванием** — при дальнейшей проверке (перед началом
написания ETL) выяснилось: в колонке "№ документа Покупки/Возврата" всего **~60 уникальных значений на файл** при
десятках тысяч строк (например, в файле юрлица 001 — 60 значений на 84 843 строки, каждое повторяется в среднем
1414 раз). Значения вида `DOC0000001..060` просто попадают в начало диапазона `DOCNUM` продаж (который у сети
доходит до `DOC0318133`), поэтому "100% совпадение" — статистический артефакт низкой кардинальности, а не связь
чек-в-чек. Это не номер конкретного чека, а какой-то batch/settlement-документ.

Проверены альтернативные ключи — тоже не сработали:
- **Адрес точки продаж**: пересечение адресов Kaspi и адресов из справочника аптек (05) — **0 из 42** уникальных
  адресов Kaspi. Разные псевдонимизированные пулы значений.
- **Юр. лицо**: внутри каждого Kaspi-файла есть метаполе "Наименование" (например, файл `юрлицо_001` внутри
  называет себя "Юрлицо 0011") — из 5 таких имён только **1 из 5** совпадает с реальными юрлицами из справочника
  аптек (`Юрлицо 0001`…`Юрлицо 0010`). Остальные четыре (0011-0014) не существуют в справочнике вообще.

**Вывод: Kaspi-выписки (08-12) невозможно достоверно привязать к конкретной аптеке, сотруднику или юрлицу из
остальных файлов.** Используем их только как самостоятельный сетевой/файловый агрегат (`payment_mix`) — общая
сумма операций, доля возвратов, ставка комиссии — без разбивки по аптеке. Это отражено в `docs/hypotheses.md`
(там же — какие карточки пришлось убрать/пересобрать после этой находки).
- **`04_справочник_товаров_краткий`** не имеет WARE_ID — это, по всей видимости, отдельная выгрузка того же
  справочника товаров для внешних целей (штрихкод + название + производитель). 99% штрихкодов (`ШК`) совпадает со
  штрихкодами (`BARCODE`) из 03. Самостоятельной ценности для витрин не несёт — 03 полностью его перекрывает и имеет
  WARE_ID для джойна. **Решение: в ETL не использовать 04, оставить как есть в data/raw.**
- **`06` и `07`** — оба являются подмножествами `05` по коду аптеки (578 и 567 записей соответственно против 589 в
  05; кодов, которых нет в 05, ни в 06, ни в 07 не найдено). Они не добавляют новых аптек, только дублируют часть
  атрибутов 05 в других разрезах.

## 3. Что лежит в каждой таблице (кратко по колонкам)

**01 продажи / 02 приход** (одна и та же схема): `VH_DATA`/`DATA` — метки времени документа и его проведения,
`OWNER_ID`/`USERNAME` — сотрудник (в 02 почти всегда пусто — приход не привязан к кассиру), `POSTAVSHIK` — поставщик
товара (в 01 это атрибут товара, "унаследованный" от прихода, а не участник продажи), `APTEKA_ID`/`APTEKA_NAME` —
аптека, `DOCNUM`/`VNUM` — номер документа/чека, `TIP_DOCUMENTA` — тип (в 01 всегда "Чек ККМ", в 02 всегда "Приход от
поставщика" — возвратов поставщику в апрельских данных нет), `WARE_ID`/`WARE_NAME` — товар, `DD_PRICE`/`P_PRICE` —
цена продажи/прихода (почти всегда совпадают между собой), `QUANT` — количество, `GODENDO` — срок годности партии,
`PRICE_ZAKUP` — закупочная цена (нужна для расчёта маржи).

**03 справочник товаров**: `WARE_ID` (ключ), `SNAME` (название), `SIZG` (производитель), `SCOUNTRY` (страна),
`BARCODE`, `MNN` (международное непатентованное наименование — код действующего вещества, полезно для группировки
аналогов/дженериков).

**05 справочник аптек**: `Код` (ключ), `Название`, `Адрес`, `Юр. лицо` (10 значений в самом справочнике — `Юрлицо
0001`…`0010`; **не путать** с 5 файлами Kaspi — см. п.2.1, эти два "юрлица" достоверно не совпадают), `Регион
прайса`, `Область`, `Город`.

**08–12 Kaspi**: у файла "человеческая" шапка — первые 6 строк это метаинформация (период, ИИН/БИН, наименование
юрлица), реальные заголовки колонок начинаются с 7-й строки файла. Полезные колонки: `Тип операции` (Покупка /
Возврат), `№ документа Покупки/Возврата` (**не является рабочим ключом**, см. п.2.1), `Дата операции`, `Тип оплаты`,
`Сумма операции (т)`, набор колонок с комиссиями Kaspi (`Комиссия Kaspi Pay (т/%)` и т.п.) — это прямые издержки на
безналичный эквайринг, но привязать их к конкретной аптеке/чеку в этих данных нельзя, только к сети в целом.

**13 ежедневные остатки**: `Дата`, `Аптека`, `G$PROFILE_ID`, `PART_ID` (номер партии — реальный грануляр строки),
`WARE_ID`/`Товар`/`ШК`/`Изготовитель`, `Поставщик`, `Остаток на начало дня`, `Приход (шт)`, `Продажи (шт)`,
`Возвраты (шт)`, `Списания (шт)`, `Приход перемещение (шт)` / `Расход перемещение (шт)` (межаптечные перемещения —
прямая база для решения "увезти/привезти товар"), `Остаток на конец дня`, `Закупочная цена`, `Розничная цена`.

## 4. Проблемы качества данных

### Критично для архитектуры ETL

1. **Файл 13 хранится на уровне партии (`PART_ID`), а не SKU.** У 50.9% строк ключ `(Дата, Аптека, WARE_ID)`
   повторяется (одна и та же дата/аптека/товар — несколько партий), и как следствие у 51.3% строк
   `Остаток на конец дня` отрицательный (это нормально *для партии* — продажа списывается с ещё не оприходованной
   партии, — но бессмысленно как метрика "остаток товара"). **Вывод: перед любой агрегацией по SKU обязательна
   `SUM(...) GROUP BY Дата, Аптека, WARE_ID`** — это будет сделано SQL-вьюхой в `sql/marts/`, а не в pandas (файл
   слишком большой для комфортной работы в памяти на этапе 3).
2. **Только один месяц данных (апрель 2023).** Ни один "тренд" на дашборде не может показать больше 30 точек, и
   нет базы для сравнения "месяц к месяцу" или сезонности. Решения "закрыть аптеку" по одному месяцу — методологически
   рискованы; дашборд должен явно это показывать (не более 30 дней на оси X) и, где возможно, использовать
   внутримесячную волатильность (неделя/будни-выходные) вместо "тренда".
3. **463 из 589 аптек в справочнике (79%) не имеют ни одной продажи или прихода в апреле 2023.** Это либо
   исторически закрытые/тестовые записи в справочнике, либо аптеки вне выгрузки. Для дашборда "закрыть/оставить"
   это значит: справочник аптек и факт активности сети — разные множества, витрины должны строиться от факта
   (только 122–129 реально работавших аптек), а не от справочника.
4. **Справочники городов 05 и 07 расходятся: 19.2% пересекающихся аптек имеют разный город.** Нужно явно выбрать
   источник правды (рекомендация: 07, там нет пропусков и он ýже/чище) и задокументировать выбор в ETL-логе, а не
   молча взять один из двух.
5. **Найдено на Этапе 4 (при построении `sql/marts/sku_movement.sql`): последний день периода (30.04.2023) имеет
   `Остаток на конец дня = 0` буквально на 100% строк файла остатков** (888 283 из 888 283 строк за этот день,
   и в staging, и после агрегации до уровня SKU) — при том что за 29.04 таких нулей только 0.7%. Реальный остаток
   не может одновременно занулиться у всей сети день в день — это артефакт выгрузки/экспорта последнего дня
   периода, а не факт по товару. **Вывод: "текущий остаток" и "последняя цена" по SKU нужно брать на последний день
   СТРОГО ДО финального дня выгрузки** (29.04, не 30.04) — иначе любая метрика "остаток сейчас" будет ложно нулевой
   для всей сети. Это единственная метрика, которую задевает баг: суммы продаж/приходов/списаний за 30.04 сами по
   себе выглядят нормально, страдает только колонка "Остаток на конец дня" в этот день.

### Пропуски / мелкие огрехи (не блокируют, но нужно обработать осознанно)

6. `DATE_FIRST_PRIHOD` пуст на 96.6% (продажи) / 99.65% (приход) — колонка почти не заполняется исходной системой,
   не несёт аналитической ценности, в трансформацию не берём.
7. `GODENDO` (срок годности) — 96.0% (продажи) / 98.8% (приход) значений попадают в правдоподобный диапазон
   2023–2035 год. Остальные — технически мусорные даты (например, год 520, 8202, 1899 — похоже на sentinel-значения
   "без срока годности" или артефакт псевдонимизации/экспорта). На этапе очистки — обнулять даты вне разумного
   диапазона, а не использовать их как есть.
8. Полные дубли строк: 512 (0.06%) в продажах, 387 (0.28%) в приходе — небольшая доля, но нужно `drop_duplicates()`
   явно и залогировать сколько строк удалено.
9. `QUANT` дробный в 7.8% строк продаж (0.05% в приходе) — товары, которые продаются частями упаковки (ампулы,
   вес). Не ошибка, но при подсчёте "количество позиций в чеке" считать нужно по числу строк (SKU), а не по сумме
   QUANT.
10. 11 из 291 сотрудников (продажи) и 17 из 245 (приход) встречаются более чем в одной аптеке за месяц (подменные/
    разъездные сотрудники). Для витрины `employee_performance` у таких сотрудников не будет одной "домашней" аптеки —
    агрегировать нужно по паре (сотрудник, аптека), не только по сотруднику.
11. Штрихкод (`BARCODE`) не уникален в справочнике товаров: 139 дублей на 28 185 товаров (0.5%) — не использовать
    штрихкод как альтернативный ключ товара, только `WARE_ID`.
12. `SIZG` (производитель) пуст на 11.2%, `SCOUNTRY` (страна) — на 19.8% товаров. Разрезы по производителю/стране
    будут неполными, это нормально для дженериков/безымянных товаров (маски, пакеты и т.п.), просто нужна явная
    категория "Не указано" вместо NULL на дашборде.

### Не проблема, но важно для интерпретации

13. `POSTAVSHIK` в файле продаж — атрибут товара (текущий поставщик), а не участник конкретной сделки продажи;
    не путать с `POSTAVSHIK` в приходе, где это реальный контрагент поставки.
14. `OWNER_ID` в продажах — не сотрудник и не касса 1:1 (одному `OWNER_ID` соответствует в среднем 8 разных
    `USERNAME`); похоже на группировку по смене/точке доступа. Для витрин по сотруднику использовать `USERNAME`,
    `OWNER_ID` не задействовать.
15. Kaspi-файлы содержат только безналичные операции (Покупка/Возврат), но привязать их к конкретной аптеке нельзя
    (п.2.1) — поэтому доля безнала считается **только на уровне сети целиком**: `SUM(Kaspi) / SUM(выручка сети)`,
    а не по аптеке. Наличные в данных не имеют прямого признака и методологически считаются как остаток.

## 5. Что дальше (черновой план, детали — в `docs/hypotheses.md`)

- Канонический товарный справочник — только `03` (WARE_ID — PK), `04` не используем.
- Канонический справочник аптек — `05` как основа, город — из `07` (там чище), `06` не используем отдельно.
- Факт-таблицы: `01_sales`, `02_receipts`, `13_stock_daily` (агрегированный до SKU), `kaspi_payments` (объединение
  08–12 с добавлением колонки юрлица из имени файла).
- Все денежные и количественные поля — привести к `numeric` (заменить `,` → `.`), даты — к `timestamp`/`date`.
- Явно логировать: сколько строк отброшено дублями, сколько дат обнулено вне диапазона, какой источник города выбран.

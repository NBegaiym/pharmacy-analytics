# Гипотезы дашбордов (Этап 2)

Основано на профилировании данных ([`docs/data_profile.md`](data_profile.md)). Два дашборда: **CEO** (сеть целиком,
сравнение аптек, деньги) и **COO** (конкретная аптека — сотрудники, товар, чек). Каждая карточка ниже отвечает на
конкретный вопрос из ТЗ и указывает, из какой вьюхи в `sql/marts/` она будет питаться.

Общее ограничение для обоих дашбордов (см. `data_profile.md`, п.4.2): данные — один месяц (апрель 2023). Тренд —
это динамика внутри месяца (день/неделя/будни-выходные), не сравнение месяц-к-месяцу. На дашбордах это должно быть
видно явно (подпись периода), а не маскироваться под "тренд сети" на годы вперёд.

**Второе ограничение (важно, найдено при перепроверке до начала кодирования ETL):** Kaspi-выписки (08-12) **нельзя
достоверно привязать к конкретной аптеке, юрлицу или сотруднику**. Изначально казалось, что связь есть через
"№ документа Покупки/Возврата" (100% совпадений с `DOCNUM` продаж) — но это статистический артефакт: в колонке
всего ~60 уникальных значений на файл (каждое повторяется тысячи раз), то есть это не номер чека, а какой-то
batch/settlement-документ. Проверены и отброшены альтернативы: адреса точек продаж в Kaspi и в справочнике аптек —
из разных псевдонимизированных пулов (пересечение 0), внутреннее поле "Юрлицо" в файле почти не совпадает с
реальными юрлицами из справочника аптек. **Вывод: Kaspi-данные используются только на уровне сети/файла-выписки
(агрегат), не разбиваются по аптеке/сотруднику/юрлицу.** Ниже это учтено — карточки, которые требовали такой
разбивки, убраны или сведены к сетевому уровню.

## Дашборд 1. CEO — стратегический (сеть целиком)

### Решение 1: закрыть аптеку или оставить?

| Карточка | Метрика | Разрез | Источник |
|---|---|---|---|
| Рейтинг аптек по выручке и марже | `SUM(DD_PRICE*QUANT)`, `SUM((DD_PRICE-PRICE_ZAKUP)*QUANT)`, `margin_%` | по аптеке, сортировка | `store_health` |
| Матрица "здоровья" аптеки | выручка (X) vs маржа % (Y), размер точки = кол-во чеков | по аптеке | `store_health` |
| Динамика выручки по дням | выручка/день | по аптеке, наложение на средний по сети | `store_health` |
| Стабильность продаж | коэффициент вариации дневной выручки внутри месяца | по аптеке | `store_health` |
| Скрытые издержки: комиссия Kaspi | `SUM(комиссия)/SUM(сумма_операции)` — % от выручки "съедает" эквайринг | по сети / по дням (не по аптеке — нет ключа связи, см. ограничение выше) | `payment_mix` |
| Деньги, замороженные в неликвиде | стоимость остатка (`Остаток_на_конец_дня * Закупочная_цена`) для товаров с нулевыми продажами ≥ N дней | по аптеке | `sku_movement` |
| Списания | `SUM(Списания_шт * Закупочная_цена)` как % от оборота | по аптеке | `sku_movement` |

**Вывод для CEO:** аптека — кандидат на закрытие, если одновременно: выручка ниже медианы сети, маржа % ниже
медианы, много замороженного неликвида, и это не объясняется коротким периодом работы (аптека открылась недавно).

### Решение 3 (сетевой срез): куда везти товар "в среднем"

На CEO-уровне — не конкретные SKU (это COO), а агрегат: у скольких аптек одновременно избыток одних категорий и
дефицит других → показывает, насколько сеть вообще нуждается в перераспределении, а не просто в закупке.

| Карточка | Метрика | Источник |
|---|---|---|
| Индекс дисбаланса остатков по сети | доля SKU×аптека пар, которые одновременно "избыток" в одной аптеке и "дефицит" в другой (та же товарная группа/MNN) | `sku_movement` |
| Оборачиваемость по сети | `SUM(Продажи_шт) / AVG(Остаток)` по товарной категории, сеть vs по аптекам-выбросам | `sku_movement` |

### Доп. гипотезы (сетевой P&L)

| Карточка | Метрика | Источник |
|---|---|---|
| P&L-подобная сводка сети | выручка, COGS (`SUM(PRICE_ZAKUP*QUANT)`), валовая маржа, комиссия эквайринга (сетевой агрегат), списания — в одну "воронку" | `store_health` + `payment_mix` |
| Доля безнала и её динамика по сети | `Kaspi_сумма / выручка_сети` по дням — если высокая и растёт, комиссия Kaspi — растущая статья расходов. Только по сети целиком, не по аптекам (нет ключа связи) | `payment_mix` |
| Средний чек и позиций в чеке по сети | `AVG(revenue/чек)`, `AVG(SKU_count/чек)` по аптекам, сравнение с сетевым средним | `basket_analysis` |
| Топ/анти-топ аптек по динамике внутри месяца | выручка 1-й недели vs 4-й недели, % изменения | `store_health` |
| Комиссия Kaspi по файлу-выписке | 5 Kaspi-файлов дают 5 разных фактических ставок комиссии — можно сравнить их между собой (это разные договоры эквайринга), но подписать честно: файл ≠ юрлицо из справочника аптек (не подтверждается) | `payment_mix` |
| Разброс закупочных цен по поставщикам | `MAX(цена)/MIN(цена)` за один и тот же `WARE_ID` у разных `POSTAVSHIK` в приходе — прямой сигнал "есть с кем поторговаться" или сменить поставщика | `procurement_efficiency` (новая вьюха) |
| Согласованность розничных цен по сети | разброс `DD_PRICE` для одного и того же `WARE_ID` между аптеками/во времени — либо осознанная региональная политика, либо стихийные правки цены на кассе | `sku_movement` |

## Дашборд 2. COO — операционный (конкретная аптека)

### Решение 2: уволить сотрудника или оставить?

| Карточка | Метрика | Разрез | Источник |
|---|---|---|---|
| Рейтинг сотрудников внутри аптеки | выручка/сотрудника, маржа/сотрудника, кол-во чеков, средний чек | по сотруднику, **относительно своей аптеки** (не всей сети — разный трафик) | `employee_performance` |
| Продуктивность на активный день | `выручка / кол-во дней с продажами` — сглаживает частичную занятость/подработку | по сотруднику | `employee_performance` |
| Позиций в чеке у сотрудника | `AVG(SKU_count/чек)` — умение продавать "в довесок" | по сотруднику vs средний по аптеке | `employee_performance` + `basket_analysis` |
| Сотрудники в нескольких аптеках | флаг "разъездной" — не сравнивать с одноточечными "в лоб" | по сотруднику | `employee_performance` |

**Важная оговорка (из профилирования):** 11–17 сотрудников работают в нескольких аптеках за месяц — их
производительность считается по паре (сотрудник, аптека), иначе смешиваются разные точки.

### Доп. гипотеза: часы пик и загрузка кассиров

Связывает решение 2 (сотрудник) и решение 4 (чек): если в час пик работает столько же кассиров, сколько в
"тихий" час, кассир либо не успевает допродавать (меньше позиций в чеке), либо простаивает.

| Карточка | Метрика | Разрез | Источник |
|---|---|---|---|
| Загрузка по часам | кол-во чеков в час vs кол-во уникальных `USERNAME`, оформивших хоть один чек в этот час | по аптеке, час дня | `staffing_load` (новая вьюха) |
| Позиции в чеке vs загрузка | позиций в чеке в "тихие" часы vs "пиковые" — падает ли допродажа под нагрузкой | по аптеке, час дня | `staffing_load` + `basket_analysis` |

### Решение 3: товар увезти или привезти?

| Карточка | Метрика | Разрез | Источник |
|---|---|---|---|
| Скорость продаж (шт/день) | `SUM(Продажи_шт)/30` | по SKU × аптека | `sku_movement` |
| Дней запаса (days of cover) | `Остаток_на_конец_дня / скорость_продаж` | по SKU × аптека | `sku_movement` |
| Дефицит (упущенные продажи) | дни, когда агрегированный остаток по SKU ≤ 0, но был спрос в этой товарной группе в сети | по SKU × аптека | `sku_movement` |
| Кандидаты на перемещение | SKU с days_of_cover ≫ сети в аптеке A и дефицитом того же SKU/MNN в аптеке B | по SKU, пара аптек | `sku_movement` |
| Риск списания по сроку годности | доля продаж товара с `GODENDO` в ближайшие 30/60 дней (прокси на остаток, т.к. срок годности остатка напрямую не выгружен) | по SKU × аптека | `sku_movement` |
| Лаг "приход → первая продажа" | дней между `DATA` прихода и первой продажей того же `WARE_ID` в той же аптеке | по SKU × аптека | `sku_movement` |

### Решение 4: позиций в чеке — сколько, почему, как увеличить?

| Карточка | Метрика | Разрез | Источник |
|---|---|---|---|
| Распределение позиций в чеке | гистограмма `COUNT(WARE_ID) GROUP BY DOCNUM` | по аптеке/сети | `basket_analysis` |
| Динамика по времени | средние позиции в чеке по часам дня / дням недели | по аптеке | `basket_analysis` |
| Позиции в чеке по сотруднику | `AVG` позиций у сотрудника vs у аптеки | по сотруднику | `basket_analysis` |
| Топ категорий-"одиночек" | товары, которые почти всегда покупают в чеке из 1 позиции (кандидаты на кросс-продажу/выкладку у кассы) | по товару | `basket_analysis` |
| Топ пар товаров в одном чеке | `SELF JOIN` продаж по `DOCNUM`, топ связок | по товару/MNN | `basket_analysis` |
| Связь размера чека с выручкой | корреляция `SKU_count` и `revenue` чека | по аптеке | `basket_analysis` |

### Доп. гипотеза (специфично для COO): не сравнивать разные по размеру/трафику аптеки "в лоб"

Все метрики COO (сотрудник, товар, чек) считаются **относительно своей аптеки** (% к среднему аптеки), а не в
абсолютных числах по сети — иначе крупная аптека всегда "лучше" мелкой не по качеству работы, а по трафику.

### Доп. гипотеза: аномалии в чеках (индикатор фрода/ошибок кассира)

Не "довод для увольнения сам по себе", а список для проверки — единичный случай ничего не значит, повторяющийся
паттерн у одного сотрудника/точки — повод разобраться. Грануляция — чек (`DOCNUM`), агрегируется по
сотруднику/аптеке.

| Сигнал | Как считается | Источник |
|---|---|---|
| Расхождение цены продажи и учётной цены | доля чеков с `DD_PRICE != P_PRICE` у сотрудника, против среднего по аптеке | 01 продажи |
| Задержка между созданием и проведением чека | разрыв `VH_DATA` и `DATA` — крупный разрыв может значить отложенный/задним числом ввод чека | 01 продажи |
| Дублирующиеся чеки | полные дубли строк (0.06% в продажах) — concентрация на конкретном сотруднике/аптеке выше средней по сети | 01 продажи |
| Нетипично крупный разовый чек | сумма чека сотрудника выходит за 3 стандартных отклонения от его же обычных чеков | 01 продажи |

Возвраты по Kaspi (`Тип операции = Возврат`) в отдельности всё же стоит показать — но только как сетевой
показатель ("доля возвратов от общего объёма безнала"), без привязки к конкретному сотруднику/точке — ключа для
такой привязки в данных нет (см. ограничение в начале документа).

Всё это — в отдельную вьюху `receipt_anomalies.sql`, с флагами на уровне чека, чтобы на дашборде можно было
раскрыть "почему" конкретный сотрудник попал в список подозрительных, а не просто показать голую цифру.

## Общие фильтры на обоих дашбордах

- Период (дата) — в пределах апреля 2023.
- Аптека (multi-select) — на CEO по умолчанию "все", на COO — обязателен выбор одной для операционных карточек.
- Юр. лицо / регион / город — для CEO.
- Категория / MNN (действующее вещество) — для товарных карточек.

## Соответствие вьюхам в `sql/marts/`

| Вьюха | Для каких карточек |
|---|---|
| `store_health.sql` | Решение 1 (закрыть/оставить), сетевой P&L |
| `employee_performance.sql` | Решение 2 (уволить/оставить) |
| `sku_movement.sql` | Решение 3 (увезти/привезти), риск списания, лаг приход→продажа, согласованность цен |
| `basket_analysis.sql` | Решение 4 (позиции в чеке) |
| `payment_mix.sql` | Комиссии Kaspi, доля безнала, доля возвратов — **только по сети/файлу-выписке**, без привязки к аптеке/сотруднику (нет ключа связи, см. ограничение в начале документа) |
| `procurement_efficiency.sql` (доп.) | Разброс закупочных цен по поставщикам на один товар |
| `staffing_load.sql` (доп.) | Часы пик и загрузка кассиров |
| `receipt_anomalies.sql` (доп.) | Аномалии в чеках — индикатор фрода/ошибок кассира |

Итого 8 вьюх в `sql/marts/` — 4 базовых из ТЗ + 4 добавленных под расширенные гипотезы.
